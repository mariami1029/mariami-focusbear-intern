# Browser Developer Tools – QA Reflection

## 1. Main Features of Browser Developer Tools

Browser Developer Tools (DevTools) provide a set of tools for inspecting and debugging web applications.

### Elements / Inspector

The Elements panel allows QA testers to inspect the HTML structure and CSS styles of a page.

It can be used to investigate:

* Incorrect text or content
* Missing elements
* Incorrect CSS styles
* Layout problems
* Visibility issues
* Incorrect spacing or positioning
* Responsive behaviour

A tester can also temporarily modify HTML and CSS in DevTools to investigate whether a particular style or element is responsible for a visual problem. These changes are only local and do not modify the actual application code.

### Console

The Console displays JavaScript messages and errors generated by the application.

It can show:

* JavaScript errors
* Warnings
* Network-related errors
* Debug messages
* Exceptions
* Stack traces

The Console is especially useful when an application appears to stop responding or a UI action does not produce the expected result.

### Network

The Network panel allows testers to monitor requests made between the browser and the server.

It provides information such as:

* Request URL
* HTTP method
* Status code
* Request and response headers
* Request payload
* Response body
* Request timing
* Resource type

This is particularly useful for testing APIs and investigating problems involving data loading or form submission.

### Sources

The Sources panel can be used to inspect loaded source files and debug JavaScript using breakpoints.

For QA, this can help provide additional context when investigating a frontend problem.

### Application / Storage

Depending on the browser, DevTools can also provide access to information such as:

* Cookies
* Local Storage
* Session Storage
* Cache
* Service workers

This can be useful when investigating login, session, caching, or data persistence issues.

### Responsive / Device Tools

DevTools can simulate different screen sizes and device configurations.

This helps QA testers investigate responsive UI behaviour without having to physically use every screen size.

# 2. Checking JavaScript Errors

To investigate JavaScript errors, I would open DevTools and navigate to the **Console** tab.

I would then reproduce the problematic action and observe whether a new error appears.

Useful information can include:

* Error message
* Error type
* File and line number
* Stack trace
* Related warnings
* Timestamp or sequence of events

For example, if clicking a "Save" button does nothing, I would reproduce the issue while watching the Console. If a JavaScript exception appears at the same time, this provides evidence that the frontend error may be related to the failed interaction.

I would not assume that every Console warning is a product bug. Some messages may be caused by browser extensions, development configurations, third-party services, or other unrelated factors. I would therefore compare the error with the actual user-visible behaviour.

# 3. Using the Network Tab to Monitor API Requests

The Network tab is one of the most useful DevTools features for QA testing.

A basic workflow is:

1. Open DevTools.
2. Select the **Network** tab.
3. Clear previous requests if necessary.
4. Perform the action being tested.
5. Find the relevant request.
6. Inspect its method, URL, status code, headers, payload, and response.
7. Compare the API behaviour with the expected UI behaviour.

For example, if clicking **Login** does not log the user in, I would check whether a login request was sent.

I would investigate:

### Request

* HTTP method such as GET, POST, PUT, PATCH, or DELETE
* Request URL
* Request payload
* Request headers

### Response

* HTTP status code
* Response body
* Response headers
* Error message, if available

### Timing

I would also check how long the request takes and whether there are unusually slow requests.

# 4. Determining Whether an API Call Succeeded

DevTools can help distinguish between frontend problems and backend/API problems.

For example:

### Successful request

If the request returns a successful HTTP response and the response contains the expected data, but the UI does not update, the problem may be somewhere in the frontend handling of the response.

### Failed request

If the request returns an error status such as `400`, `401`, `403`, `404`, `409`, or `500`, I would investigate the request and response to understand what failed.

I would also check whether:

* The request payload is correct.
* Required parameters are present.
* Authentication information is valid.
* The response contains an error message.
* The request was sent to the expected endpoint.

The status code alone is not always enough to determine the root cause, so I would inspect the complete request and response context.

---

# 5. Simulating Different Network Conditions

DevTools can simulate slower network conditions to help test how a web application behaves when the connection is not ideal.

For example, I could test under:

* Fast connection
* Slow connection
* High latency
* Offline conditions

This can reveal problems such as:

* Missing loading indicators
* Requests timing out
* UI becoming unresponsive
* Duplicate submissions
* Incorrect error messages
* Data appearing incomplete
* Poor handling of failed requests

For example, if a user clicks **Save** while using a slow connection, I would check whether the application shows a loading state and prevents accidental duplicate submissions.

Network throttling is not a perfect replacement for testing on a real slow network, but it is a useful way to reproduce controlled conditions during web testing.

# Reflection

## 6. How I Would Use DevTools to Confirm an API Failure

If I suspected an API failure, I would use the Network tab while reproducing the issue.

My process would be:

1. Open Network.
2. Clear previous requests.
3. Perform the action that triggers the API call.
4. Identify the relevant request.
5. Check the HTTP method and URL.
6. Check the status code.
7. Inspect the request payload.
8. Inspect the response body.
9. Check request timing.
10. Compare the result with the expected behaviour.

For example, if submitting a registration form produces an error, I would check whether the request was actually sent and whether the server returned an error.

This helps determine whether the problem is likely to be in the frontend, API, authentication, validation, or network layer.

---

## 7. Debugging a UI Issue That Only Happens in One Browser

If a UI issue occurs only in one browser, I would first reproduce the issue consistently in that browser and then compare the same scenario in another browser.

I would inspect:

* Console errors
* Network requests
* HTML structure
* Computed CSS properties
* Browser-specific warnings
* JavaScript errors
* Screen size and responsive behaviour
* Cookies and storage
* Browser version

For example, if a button is correctly positioned in Chrome but overlaps another element in Firefox, I would inspect the affected element's CSS and layout properties in both browsers.

I would compare things such as:

* `display`
* `position`
* `width`
* `height`
* `margin`
* `padding`
* `overflow`
* Computed styles

I would then provide the developer with evidence showing what differs between the browsers instead of simply reporting that "the page looks broken in Firefox."

## 8. Most Useful DevTools Information for a Frontend Bug Report

The most useful information depends on the type of bug.

For a JavaScript issue, I would provide:

* Exact Console error
* Stack trace when relevant
* File and line number
* Steps that trigger the error

For an API-related issue:

* Request URL
* HTTP method
* Status code
* Request payload when safe to share
* Response body/error
* Request timing

For a UI issue:

* Relevant HTML element
* Computed CSS properties
* Browser and version
* Screen resolution
* Responsive/device configuration
* Screenshot or screen recording

For a performance issue:

* Request timing
* Slow network requests
* Console errors
* Relevant loading information

I would avoid attaching sensitive information such as authentication tokens, cookies, passwords, API keys, or personal data.

---

# 9. Chrome vs Firefox DevTools

Both Chrome and Firefox provide similar core capabilities, including:

* Element inspection
* Console debugging
* Network monitoring
* Responsive testing
* JavaScript debugging
* Storage inspection

However, their interfaces and some debugging features differ.

Because browser-specific behaviour can be part of a bug, I would avoid assuming that behaviour observed in one browser automatically applies to another.

When investigating compatibility issues, I would record the exact browser name and version and compare the behaviour across environments.

---

# Key Takeaway

Browser DevTools are an important QA investigation tool because they provide evidence about what happens behind the UI.

Instead of only reporting:

> "The button doesn't work."

I can use DevTools to determine whether:

* The click event occurs.
* JavaScript throws an error.
* An API request is sent.
* The API returns an error.
* The response contains unexpected data.
* The frontend fails to process a successful response.
* A browser-specific CSS or JavaScript issue is involved.

My QA principle is:

**"Don't just report what the UI shows — investigate what happens underneath."**
