# Navigating the Internal Focus Bear Repository

## 1. Finding Open QA Issues Assigned to Me

When I finish my current task and need to find other work, I would start by filtering the internal Focus Bear repository instead of browsing issues randomly.

My first step would be to filter issues by:

* **Assignee:** myself
* **Status:** Open / not completed
* **Label:** QA or other relevant QA-related labels

If needed, I would also use the **milestone** filter to narrow the results to a specific area of work.

This combination should allow me to quickly see the open QA issues that are currently assigned to me.

I would also check the issue details before starting work. I would look at the description, acceptance criteria, comments, labels, priority, dependencies, and any linked issues to make sure I understand what is expected.

---

## 2. Filtering Issues by Milestone, Label, Assignee, and Status

Filtering is useful because a large repository can contain many issues that are not relevant to my current work.

### Milestone

Milestones help group issues around a larger goal or stage of work.

I can use a milestone filter when I want to see all issues related to a particular release, project, or objective.

### Label

Labels provide another way to categorize work.

For example, I could filter for QA-related labels to find testing tasks or bugs.

### Assignee

The assignee filter allows me to see which issues are assigned to a particular person.

For my own workload, I would select myself.

### Status

Status helps me understand whether an issue is still open, being worked on, blocked, or completed.

Using multiple filters together is more useful than relying on only one filter.

For example:

**Assignee = Me + Label = QA + Status = Open**

would give me a much more focused view of my current QA work.

---

## 3. Understanding the Roadmap View

The Roadmap view provides a higher-level picture of the team's work.

Instead of looking at individual issues one by one, I can use the Roadmap to understand where larger pieces of work currently stand.

I would use it to distinguish between:

### In Progress

Work that the team is actively working on.

### Planned

Work that is expected or intended to happen but has not started yet.

### Blocked

Work that cannot currently move forward because it depends on something else or has another issue preventing progress.

This distinction is important because an issue being visible in the repository does not necessarily mean that it is ready for someone to start working on it.

---

## 4. How the Roadmap Helps Me Understand My Place in the Team

The Roadmap gives context that individual issues may not provide.

For example, I might have a QA issue assigned to me, but the Roadmap could show that the feature is still being developed. In that situation, starting full testing immediately may not be the best use of my time.

Similarly, if a task is blocked, I can understand why it is blocked instead of assuming that I should continue working on it.

The Roadmap can also help me see how my QA work fits into a larger feature or release.

This is useful because QA is not separate from development. Testing is connected to the team's overall workflow and depends on the state of the product.

---

## 5. Where I Would Look First for New Work

Once I finish my current task, I would first check my **assigned open issues**.

If there is no suitable task there, I would check the **Roadmap** to understand what work is currently in progress and what is planned next.

After that, I would look at the relevant open QA issues and check whether any are ready to be picked up.

Before starting a new issue, I would check:

* Is it assigned to me?
* Is it actually ready to start?
* Is it blocked by another issue?
* Are the requirements clear?
* Are there dependencies?
* Is there already someone working on it?
* What is its priority?

If I am unsure whether I should pick up an unassigned issue, I would ask the appropriate team member rather than assuming.

---

## 6. My Practical Workflow

My workflow for finding new work would be:

**Finish Current Task → Check Assigned Open Issues → Review Roadmap → Check QA Issues → Check Status & Dependencies → Pick Ready Work → Start Testing**

This prevents me from simply choosing an issue because it looks interesting.

It also helps avoid situations where two people unknowingly start working on the same task or where I start a task that is currently blocked.

---

## 7. Reflection

The main thing I learned from this task is that navigating a repository is not only about finding an issue.

It is about understanding the **context around the issue**.

Filters help me quickly find the work that is relevant to me, while the Roadmap helps me understand how that work fits into the bigger picture.

As I start working more independently, I think this will become especially important. I should be able to find work on my own, understand whether it is ready to be picked up, and recognize when I need to ask for clarification.

My QA principle is:

**"Before picking up a task, understand where it fits in the bigger picture."**
